# Feature Specification: Sub-group Requirement Checklist

**Feature Branch**: `feature/040-editable-document-taxonomy`

**Created**: 2026-09-17

**Status**: Draft

**Input**: "task เก่าที่เคยบอกว่าให้มี description ประกอบแต่ละหมวดอ่ะ ว่าแต่ละหมวดมีอะไรตาม list ที่ต้องมีแล้วบ้าง อะไรขาดบ้าง" — every sub-group should say what documents it is supposed to hold, and for each one whether it is already in, still missing, or waiting on something else, so that anyone opening the category can see at a glance what is complete and what is not.

## Why this is needed

หมวด 6 ยื่นขออนุญาตระบบความปลอดภัยอาคาร is no longer a filing cabinet — it is a submission checklist. The officer asks for specific documents, and each sub-group exists to hold a particular set of them. Nothing in the app records that set. Today the only place it lives is a Google Doc that has to be regenerated by hand after almost every change, as files are added and moved and sub-groups are merged or removed.

The folder names cannot carry this on their own:

- **A name does not list its contents.** "ใบรับรองและสเปก" holds fifteen files and still lacks six specific certificates; nothing on the page says which six.
- **An empty folder says nothing.** Several of หมวด 6's sub-groups hold no files, and a file count of zero does not tell anyone what is expected to arrive.
- **A full folder can still be incomplete — or wrong.** "ทดสอบ" holds twelve files, but five belong to a different project (SUZUYO Distribution Center) and cannot be submitted for this building. Only someone who has read them knows.
- **Some items are blocked, not missing.** The anti-static floor resistance report cannot be produced until the lightning protection work is done. "Missing" and "waiting" call for different follow-up and need to look different.

An earlier, uncommitted draft added a single free-text description sentence per sub-group. It answered "what goes here" but not "what is in and what is not", its wording was already out of date against the current sub-groups, and its database change was never applied.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See at a glance what each sub-group still lacks (Priority: P1)

Anyone who can see the documents opens หมวด 6. Under each sub-group's name — without opening the folder — they see a short line saying what the sub-group is for, followed by the list of documents it is supposed to hold. Each item is visibly marked as already in, still missing, or waiting on something, with a short note where one helps ("รอทำสายล่อฟ้าเสร็จก่อน", "เอกสารโครงการ SUZUYO ใช้ยื่นแทนไม่ได้").

**Why this priority**: This is the whole point of the request, and it replaces the hand-maintained Google Doc as the place the submission's status is read from. Delivered alone, with the หมวด 6 content loaded, it already answers the account holder's question.

**Independent Test**: With the หมวด 6 content loaded, open the category as a viewer on a phone and confirm every sub-group shows its purpose and its items with a readable status, without expanding anything.

**Acceptance Scenarios**:

1. **Given** a sub-group with required items, **When** anyone opens its category, **Then** each item and its status are visible on the sub-group's row without expanding the folder.
2. **Given** an item marked missing and another marked in, **When** the list is viewed, **Then** the two are distinguishable by more than colour alone.
3. **Given** an item with a note, **When** the list is viewed, **Then** the note is shown alongside that item.
4. **Given** a sub-group with a description but no required items, **When** its category is opened, **Then** the description is shown and no empty list appears.
5. **Given** a sub-group with neither a description nor items, **When** its category is opened, **Then** the row looks exactly as it does today.
6. **Given** any sub-group, **When** its items are shown, **Then** no count or tally of in/missing items is displayed anywhere.

---

### User Story 2 - Keep the list true as documents arrive (Priority: P2)

An editor uploads the Emergency Shower certificate. In management mode they find the matching item under ใบรับรองและสเปก and change it from missing to in, adding a note naming the file. Later the officer asks for something new; the editor adds it as a missing item. An item that turns out not to be needed is deleted.

**Why this priority**: Without editing, the list is a snapshot that goes stale the first time a file is added — exactly the problem with the Google Doc. It is second because the list must first exist and be readable.

**Independent Test**: As an editor, add an item to an empty sub-group, change its status twice, edit its wording and note, delete it, and confirm after a page reload that each change stuck and a viewer sees the result.

**Acceptance Scenarios**:

1. **Given** management mode is on, **When** an editor adds an item with a name, **Then** it appears in that sub-group marked missing.
2. **Given** an existing item, **When** an editor changes its status, **Then** the new status shows immediately and persists after reload.
3. **Given** an existing item, **When** an editor edits its wording or note, **Then** the change persists after reload.
4. **Given** an existing item, **When** an editor deletes it, **Then** it disappears and does not return after reload, and no document is affected.
5. **Given** a sub-group, **When** an editor writes or changes its description, **Then** the new description shows for everyone.
6. **Given** several items, **When** an editor reorders them, **Then** the order holds for everyone after reload.
7. **Given** a viewer, **When** they open the category, **Then** they see the items and statuses but no control to change any of them, and a change attempted directly is refused by the server.

---

### User Story 3 - Start from the audited หมวด 6 list rather than a blank page (Priority: P3)

When the feature arrives, หมวด 6's sub-groups already carry the requirement lists established by reading every file's contents — both what is in and what is missing — so nobody has to retype the Google Doc.

**Why this priority**: It only saves typing, and the account holder could enter it by hand through Story 2. But the content exists, was checked against the real files, and would take far longer to re-enter than to load.

**Independent Test**: After the content is loaded, compare each หมวด 6 sub-group's items against the Initial content appendix below.

**Acceptance Scenarios**:

1. **Given** the content has been loaded, **When** หมวด 6 is opened, **Then** each sub-group shows the description and items listed for it in the appendix, in that order, with those statuses and notes.
2. **Given** a sub-group was renamed or removed since the appendix was written, **When** the content is loaded, **Then** that sub-group is skipped rather than its items being attached to the wrong sub-group.
3. **Given** the content has already been loaded once, **When** loading runs again, **Then** no item appears twice.

---

### Edge Cases

- A sub-group is deleted: its description and items go with it. Items describe what a folder should hold; they are not documents and need no move-or-delete choice.
- A sub-group's items are long (ใบรับรองและสเปก has more than ten): the row stays readable at 375px — wording wraps rather than truncating, and nothing forces horizontal scrolling.
- An item's name or note is very long: it wraps within the row and never pushes the status marker off-screen.
- A status change fails to save: the item returns to its previous status and the failure is reported, never left showing a state that was not stored.
- Two editors change the same item at once: the last save wins, and the page reflects what was actually stored after the next load.
- An item is added with a blank name: refused with a reason, as with sub-group names.
- Description or note cleared to empty: treated as having none, not stored as an empty line.
- A category other than หมวด 6: the same capability is available, but nothing is shown until an editor adds something.

## Requirements *(mandatory)*

### Functional Requirements

**Viewing**

- **FR-001**: Each sub-group MUST be able to carry an optional short description of what it holds.
- **FR-002**: Each sub-group MUST be able to carry an ordered list of required items, each with a name, a status, and an optional note.
- **FR-003**: An item's status MUST be exactly one of: มีแล้ว (in), ยังขาด (missing), รอดำเนินการ (waiting).
- **FR-004**: A sub-group's description and items MUST be visible on its row in the category list without expanding the folder.
- **FR-005**: The three statuses MUST be distinguishable without relying on colour alone (for example by a label or symbol in addition to colour).
- **FR-006**: The page MUST NOT show any count or summary tally of items by status.
- **FR-007**: A sub-group with no description and no items MUST render exactly as it does today.
- **FR-008**: A category MAY also carry an optional description, shown beneath the category header when present.

**Editing**

- **FR-009**: In management mode, an editor MUST be able to add an item to any sub-group; a new item's status defaults to missing.
- **FR-010**: An editor MUST be able to change an item's name, status and note, delete an item, and reorder items within a sub-group.
- **FR-011**: An editor MUST be able to set, change or clear a sub-group's description and a category's description.
- **FR-012**: A blank item name MUST be refused with a stated reason and change nothing; a description or note cleared to whitespace MUST be stored as none.
- **FR-013**: Every change in FR-009 to FR-011 MUST be enforced by the server for the editor role and refused for viewers and for anyone not signed in, not merely hidden (Constitution VII).
- **FR-014**: A status change MUST appear immediately and, if saving fails, MUST revert to the stored status with the failure reported (Constitution V).
- **FR-015**: Deleting a sub-group MUST remove its description and items with it and MUST NOT affect any document.

**Parity and presentation**

- **FR-016**: Viewing and editing MUST behave identically on every storage backend the app supports (Constitution III).
- **FR-017**: All text MUST be Thai-first, and the list MUST remain fully readable and operable at 375px with no horizontal scrolling (Constitution IV).

**Initial content**

- **FR-018**: A one-time load MUST populate หมวด 6's descriptions and items from the Initial content appendix, matching sub-groups by name, skipping any sub-group whose name no longer exists, and never creating duplicates when run again.
- **FR-019**: The out-of-date descriptions in the earlier uncommitted draft MUST NOT be applied.

### Key Entities

- **Sub-group description**: One optional sentence on a sub-group saying what it holds. Belongs to exactly one sub-group.
- **Category description**: One optional sentence on a category. Belongs to exactly one category.
- **Requirement item**: One document or piece of evidence a sub-group is expected to hold. Has a name, a status (in / missing / waiting), an optional note, and a position within its sub-group. Belongs to exactly one sub-group and is removed with it. It is not a document and has no link to one; the note is where a matching file can be named.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Someone opening หมวด 6 on a phone can say, for any sub-group, what is still missing within 10 seconds and without expanding a folder.
- **SC-002**: After the initial load, 100% of the items in the Initial content appendix appear under the right sub-group with the right status, and none appear twice.
- **SC-003**: An editor can record that a document has arrived (find the item, mark it in, add a note) in under 30 seconds.
- **SC-004**: Every change to descriptions and items is refused for a viewer when attempted directly — zero actions rely on the control being hidden.
- **SC-005**: No status, description or item change is ever left showing on screen after it failed to save.
- **SC-006**: The Google Doc no longer needs regenerating to know the submission's status: the category page alone answers "what is missing".

## Assumptions

- Status is set by a person, not derived from files. A file's presence does not prove it satisfies an item — the SUZUYO test reports are files that do not — so no automatic matching is attempted.
- Items are not linked to specific documents; a note naming the file is enough for this account holder, and a link would break whenever files are moved between sub-groups, which happens often.
- Items are visible to everyone who can already see the documents. Nothing in them is more sensitive than the files themselves.
- The capability is available to every category, but only หมวด 6 receives initial content.
- The Google Doc "เอกสารที่ยังขาด — หมวด 6" remains as it is; keeping it in step with the app is out of scope.
- The ZIP download work sitting uncommitted in the same working tree is a separate feature and is not part of this one.
